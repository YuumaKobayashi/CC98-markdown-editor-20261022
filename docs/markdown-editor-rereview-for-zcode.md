## 2. R01：图片按钮更新可能使观察器无限自触发

### 位置

文件：`src/foundation/integrations/markdown/markdown-editor.tsx`。

- `1592–1622`：annotate 中恢复图片折叠状态、创建并更新按钮。
- `1618`：图片按钮添加到 host 内。
- `1621`：无条件写入 `button.textContent`。
- `1654–1660`：MutationObserver 观察 host 的 childList、subtree 和 class 属性。

### 当前代码与原因

```ts
button.textContent = expanded ? "折叠图片" : "展开图片";
```

```ts
const observer = new MutationObserver(annotate);
observer.observe(host, {
  childList: true,
  subtree: true,
  attributes: true,
  attributeFilter: ["class"],
});
```

按钮在 host 子树中。annotate 每次设置 textContent，都会替换按钮的文本节点；即使新旧文字相同，也不应假设该赋值不会产生 childList mutation。

触发链为：

1. 编辑区出现图片，或者含图片的编辑区发生一次被观察的变化。
2. MutationObserver 调用 annotate。
3. annotate 重设图片按钮的 textContent。
4. 按钮子节点变化，再次触发同一个观察器。
5. 重复上述过程。

这可能形成持续微任务循环、重复布局测量及主线程占用。浏览器表现可能是输入迟钝、CPU 持续占用或页面无响应；这些表现本轮未实测，不应写成已经观察到的现象。

### 修改要求

1. 首先让按钮更新幂等：仅当 textContent 与目标文字不同时才写入。
2. 审查 annotate 中所有 DOM 写入，确保同一状态重复执行不会持续产生新的被观察变化。
3. 尽量避免观察自己创建的辅助按钮。可缩小观察根节点、按 mutation 来源过滤，或建立独立辅助层；选择方案时保留对 Vditor 内容重建的感知。
4. 不要仅用普通 debounce 或每帧调度掩盖自触发循环；否则只是把无限微任务变成持续逐帧工作。
5. 检查图片按钮定位：annotate 末尾当前只调用 positionCopyButtons，而图片定位在滚动/resize 回调中执行。首次创建、展开/折叠和 DOM 重建后，应立即进行一次正确的图片按钮定位，不依赖用户先滚动窗口。

### 验收标准

- 无图片、单图、多图、同 URL 多图、初始正文含图、上传后插图分别测试。
- 无用户操作且资源加载稳定后，annotate 调用次数停止增长。
- 点击展开/折叠后状态稳定，不持续触发观察器。
- 图片按钮首次出现位置正确；展开、折叠、滚动、窗口缩放和正文重建后仍对齐图片。
- 在浏览器中添加临时计数或性能记录证明任务收敛，验证后移除临时调试输出。
- 添加覆盖实际观察器和按钮 DOM 的回归测试，不能只测按钮文案生成函数。

## 3. R02：历史兼容预处理仍然修改不该修改的内容

### 位置

文件：`src/foundation/integrations/markdown/markdown-preprocess.ts`。

- `26–37`：围栏结束判断。
- `49–64`：任何引用行都开启补前缀逻辑。
- `75`：状态机结束后，再对全文执行“发言”模板正则。

### 已复现 A：代码块中的模板文字被增加空行

输入：

````markdown
```text
发言：**
next
```
````

当前输出：

````markdown
```text
发言：**

next
```
````

原因：前面的逐行状态机虽然跳过围栏，但最后一行 `parsed.replace(/发言：\*\*\n(?!\n)/g, ...)` 仍作用于完整文本，包括已经保护过的代码内容。

### 已复现 B：非闭合围栏被误认为闭合

输入：

`````markdown
```text
```not-a-close
> example
plain
```
`````

当前输出中 `plain` 被改成 `>plain`。

原因：闭合围栏正则只匹配行首至少三个反引号或波浪线，没有要求围栏后只剩空白。因此 ` ```not-a-close ` 提前结束了状态机的代码保护，后续代码被当作正文引用处理。

### 已复现 C：现代 Markdown 的独立列表被拉进引用

输入字符串：

```text
> quote\n- outside
```

当前输出字符串：

```text
> quote\n>- outside
```

代码没有识别历史模板，只要遇到任意 `>` 行，就会给后续非空行补 `>`。因此现代 Markdown 的块边界仍可能被改变。

### 补充观察：CRLF 模板没有与 LF 一致处理

`"> 发言：**\r\n引用内容\r\n"` 会补引用前缀，但末尾模板正则只匹配 `**\n`，不会在 `**\r\n` 处补预期空行。是否需要统一，应依据真实旧模板的预期确定，并增加测试。

### 修改要求

1. 所有历史模板修复必须在同一套上下文保护内进行，不能状态机处理后又全文替换。
2. 正确识别开/闭围栏字符、长度、允许的尾随字符及缩进。闭合围栏之后存在普通非空白文本时，不得提前结束保护。
3. 把补前缀行为限定到可识别的历史模板；不要把所有引用都当成不完整旧帖。
4. 保留正常代码、现代引用、列表、标题、分隔线等块结构。
5. 依据真实样例明确 LF/CRLF 行尾规则，保持输出稳定和幂等。
6. 继续只处理展示，不回写原帖或草稿。

### 验收标准

- A、B 的代码内容逐字符保留。
- C 保持原有独立列表语义，不自动补引用前缀。
- 覆盖反引号/波浪线、较长围栏、伪闭合行、围栏内的“发言”模板、缩进代码及嵌套引用。
- 添加真实历史模板的正向样例，证明兼容能力没有被简单删除。
- 增加幂等断言和 LF/CRLF 样例。
- 新测试必须包含上述实际失败输入，不能只重复当前 24 项测试中的成功样例。

## 4. R03：上传任务应绑定稿件生命周期

### 位置

文件：`src/foundation/integrations/markdown/markdown-editor.tsx`。

- `1129–1130`：uploadQueueRef、processingUploadsRef。
- `1169–1186`：等待上传后直接插入结果。
- `1420–1425`：卸载清理。
- `1819–1828`：外部 value 同步，包括清空或换稿。

### 原因与触发步骤

当前队列解决了多入口并发和单文件 reject 中断整批的问题，但没有标记请求属于哪份稿件。

可用延迟 Promise 验证：

1. 编辑器加载稿件 A，发起附件上传。
2. 上传未完成时，父组件清空正文、提交成功后重置，或加载稿件 B。
3. 此时编辑器实例仍然存在，vditorRef 仍非 null。
4. 让 A 的上传请求完成。
5. 当前代码直接向现有编辑器执行 insertValue，旧附件可能进入空白新稿或稿件 B。

仅检查 vditorRef 是否存在，不能区分当前实例内的新旧稿件。将插入位置定义为“上传完成时光标处”也不能解决换稿污染。

### 修改要求

1. 每个上传任务记录所属实例和稿件版本/会话标识。
2. 外部清空、加载新稿及卸载时，使旧稿相关任务失效；返回结果插入前检查标识。
3. 如支持 AbortSignal，可取消在途请求；不支持取消时，至少丢弃失效结果并停止继续消费失效队列。
4. 不要因每次正常 value 回显就增加稿件版本，否则会把普通输入期间的合法上传误判为失效。应明确“换稿”与“本稿内容更新”的边界。
5. 保持同一有效稿件内的队列顺序，以及逐文件失败不影响其余文件的行为。
6. 上传提示也应按实例或任务隔离；当前固定 key `cc98-md-upload` 在多实例上传时可能互相覆盖或关闭。
7. 明确同稿上传期间移动光标的插入策略，并记录测试结果。

### 验收标准

- A 上传未结束时清空正文，再完成请求，不向新稿插入旧结果。
- A 上传未结束时载入 B，再完成请求，不污染 B。
- 卸载后不继续消费旧队列或向重挂载的实例插入。
- 普通输入引起的 value 回显不错误取消合法任务。
- 两实例同时上传，内容、队列和反馈互不干扰。
- 成功/reject/成功的三文件序列仍保留两个有效成功结果。

## 6. R05：字符串去重没有消除重复序列化

### 位置

文件：`src/foundation/integrations/markdown/markdown-editor.tsx`。

- `325–328`：公式 input 微任务无条件 onRepaired。
- `335–337`：compositionend 无条件 onRepaired。
- `349–352`：公式观察器无条件 onRepaired。
- `1393–1395`：Vditor input 直接上报。
- `1406–1410`：emitRepaired 先 getValue，再比较字符串。

### 当前效果与剩余问题

当前 emitRepaired 已减少重复通知父组件，这是有效改进。但 `getValue()` 已经在比较之前执行，公式守卫即使没有修复任何 DOM，也会触发这次全文转换。

所以不能把此项标记为“避免重复序列化已完成”。代码围栏守卫已在部分路径依据修复返回值决定上报，公式守卫仍未统一。

### 修改要求

1. 公式修复实际改变可序列化内容时才请求同步。
2. 为特殊输入路径明确同步责任，不能机械删掉全部兜底回调而导致 IME 上屏、粘贴或迟到渲染内容未上报。
3. 在实例内合并同一轮修复与同步请求，尽量先完成修复再序列化。
4. Vditor 原生 input 通知也应检查统一出口的去重策略，避免晚到的同值通知再次触发父组件更新。
5. 点击发送、换模式和保存草稿时，必须拿到最终正文，不能依赖尚未执行的延迟同步。

### 验收标准

- 统计普通输入、IME 提交、公式、代码围栏、粘贴各场景的 getValue 与 onChange 次数。
- 无实质修复时，不仅 onChange 减少，额外 getValue 也应减少。
- 长文对比使用同一机器、浏览器和样本；报告数据，不以“感觉流畅”代替验证。
- 撤销重做、最后一键后立即发送、外部 value 回填及草稿内容均正确。

## 7. R06：KaTeX 加载失败清理不能仅凭 src 判断标签归属

### 位置

文件：`src/foundation/integrations/markdown/katex-loader.ts`。

- injectScript：复用已有同 src 脚本。
- `105–112`：失败时按 src 查询标签，并在不属于 pendingScripts 时 remove。

### 问题

注释声称“只删本加载器拥有的标签”，但实现没有记录创建者。

如果脚本由另一个加载器创建，本模块只是等待它，失败或超时后仍会按相同 src 找到并删除它。pendingScripts 表示“当前是否有等待任务”，不表示“标签归谁所有”；finish 还会在失败回调前将条目从 Map 中删除。

另外，等待完成后没有主动清除超时计时器和另一条未触发的事件监听器，需要完善资源清理。样式表仍只检查标签是否存在，没有失败恢复状态。

### 修改要求

1. 明确记录本模块创建的具体 script 节点及其状态；只删除自己创建且确认失效的节点。
2. 对复用的第三方标签，失败后清理本模块等待状态，不擅自破坏第三方 DOM。
3. 成功、失败、超时均清理计时器与 load/error 监听器。
4. 检查 window.katex 的目标方法是否可调用，不仅判断对象真值。
5. 将脚本就绪、公式样式就绪和失败反馈的责任写清楚；至少覆盖 CSS 首次失败后的恢复。
6. 保留自托管路径，联合测试 md-editor-rt、Vditor、UBB 公式的实际加载方式。

### 验收标准

- 本模块创建的失败标签能正确清理并重试。
- 第三方创建的标签在本模块超时后不被误删。
- 第三方脚本延迟完成后，其自身渲染流程仍可继续。
- 成功后没有存活到 30 秒才执行的无用超时任务。
- JS/CSS 失败、慢网、并发调用和恢复网络分别测试。
